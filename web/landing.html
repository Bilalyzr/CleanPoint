Chapter 01 — The incident

The newest backup
is already compromised.

Destructive encryption predates human alarms. The five freshest snapshots in the 3D corridor carry high-entropy ciphertext behind 100% valid SHA-256 checksums — restoring them reintroduces the exact incident you are recovering from.

  • Compromise hides upstream of alarms. By the time alerts fire, scheduled snapshots have already sealed encrypted files into storage.
  • A hash proves consistency, never cleanliness. SHA-256 verifies that stored bytes did not bit-rot — not that those bytes were safe at capture time.
  • Recency bias is catastrophic. In 10 of 16 locked evaluation scenarios, both “newest” and “integrity-only” policies restore poisoned data.

Chapter 03 — The 5-Gate Orbital Lock

Safety before recency.
Every single time.

The conservative selector walks snapshots newest-first and demands five simultaneous proofs before recommending a recovery candidate:

    Logically sealedImmutable terminal status with persisted canonical JSONL manifest hash

    Deep cryptographic integrityManifest recomputed from SQLite + every SHA-256 object re-hashed on disk

    Full 24-window baseline coverageUncontaminated calibration history precedes snapshot capture

    Exposure certified clearZero ended/overlapping suspicious windows and clean manifest entropy profile

Chapter 04 — Verified Isolated Restore

Copied out. Re-hashed.
Source proven untouched.

Restore demands an Operator bearer token, explicit confirm: true, and a live EligibleNow() re-hash check. Files materialize atomically inside an isolated sandbox/restored/<target>-<runhex>/ directory — never overwriting live roots.

01 · SEALED SOURCE objects/aa/bb/<sha256>

Pre-restore Verify() re-hashes every referenced content-addressed object.

02 · ATOMIC MATERIALIZE temp → fsync → rename

Writes into server-generated sandbox/restored/; re-reads and hashes every output file.

03 · NON-MUTATION PROOF source_unchanged = true

Post-copy Verify() proves the sealed snapshot was not altered during recovery.

Snapshot sealing is API-level logical immutability, not hardware WORM storage. Full disclosure in docs/limitations.md.
