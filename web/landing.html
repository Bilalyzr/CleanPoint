The problem

"Newest backup with valid hashes" is a dangerous recovery policy

After a destructive incident, the newest available backup may already contain modified or compromised data. Extension matching and checksums alone cannot prove recovery cleanliness.

🕐Newest ≠ cleanest

Compromise often predates detection. The newest snapshot can carry encrypted-like content with perfectly valid hashes — restoring it reintroduces the incident.

#️⃣A hash proves integrity, not cleanliness

SHA-256 proves bytes are unchanged since capture. It says nothing about whether those bytes were already compromised when the snapshot was sealed.

⚖️Recency bias is costly

Blindly restoring the latest point trades minutes of RPO for the risk of restoring contaminated data. Safety must come before recency — and an operator needs to see why.

How it works

Sealed evidence → explainable detection → defensible selection

Snapshot & seal

Content-addressed SHA-256 objects with canonical manifests. Sealed snapshots are logically immutable — capture only completes after verification.

Detect anomalies

300-second windows scored against a robust median/MAD baseline: modification ratio, renames, entropy shifts, extension novelty, deletes, size changes — every signal explained, never a black box.

Rank recovery points

Only sealed, integrity-verified, exposure-clear snapshots captured strictly before the earliest plausible onset are eligible — newest wins among equals.

Restore & verify

Operator-approved restore into a server-generated isolated directory. Every file is re-hashed before an atomic rename; the sealed source is proven untouched afterwards.

🛑

The selector may abstain. When no snapshot can be defended — for example when contamination predates every capture — CleanPoint returns no_safe_candidate with evidence-based reasons instead of falling back to the newest backup. Refusing to guess is the correct answer.

HONEST LIMITS

This is a local simulation, not a production data-protection product. No live malware is ever executed, packaged or downloaded — "encrypted" content is seeded random bytes. Logical immutability is API policy, not WORM storage. A valid hash proves consistency, not absence of compromise. See docs/limitations.md in the repository for the full positioning.
